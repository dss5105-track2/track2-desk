# 请求处理协议 v1（张锦若 · 已经团队决策）

本协议定义官方 30 条请求和留出集**作为一个整体怎么跑**。它决定标准答案，所以在任何系统结果出来之前冻结。改动须开 issue、全组同意，并在 Evaluation.pdf 中说明。

## 七条规则

1. **时间基准。** 全部请求以 2026-04-01 为今天（data_dictionary.md），按 `dispatch_requests.txt` 的时间戳顺序逐条处理。发出日一律为 2026-04-01。
2. **初始状态。** 队列账本从 `workshops.csv` 的 `current_queue_days` 初始化；订单状态从 `orders.csv` 读取。
3. **状态交叉检查。** 解析出订单后必须检查：订单是否存在；是否 COMPLETE；是否在 PACKING；截止日是否已过或就是今天；本会话是否已派过；聊天里的件数与日期是否与订单表一致。任一异常先警告或追问，不直接派单。检查由 `kernel/orders.py: state_checks()` 实现。
4. **写入规则。** 系统只产出推荐；人确认后 `Ledger.commit()` 才写入账本并更新队列。以下情况**不占用产能**：追问中、被拒绝、无按时方案而等待人工决定、状态冲突待确认。
5. **跨消息记忆。** 会话保留已处理请求的结构化结果。`constraint_scope = session` 的约束对之后所有请求生效，并记录下达人与来源请求。后续请求可引用前序请求（R10 → R15）或与之同单（R14 → R20）。
6. **标准答案的定义。** 每条请求的正确行为与正确分配，按"前面所有请求都已按标准答案处理并确认"的账本状态计算。因此标准答案里只有被标为 `extract` 且存在按时方案、并被确认的请求会改变账本。
7. **评估口径。** 行为、分配、解释三项分开打分。解释中每个数字必须能对应某次工具调用的输出，否则解释判为失败，即使分配正确。

## 行为类别映射

Spec 规定四类：`extract`（提取并执行）/ `clarify` / `refuse` / `decline-to-answer`。内部子类只用于分析，报告时映射回四类：

| 内部子类 | 映射到 | 期望系统动作 |
|---|---|---|
| allocate | extract | 推荐一家，给候选表与理由，等人确认后写账本 |
| no_on_time_option | extract | 给出最早交付日和晚几天，列出选项（接受迟交 / 重谈交期 / 放宽约束 / 人工升级），**不自动写账本** |
| state_conflict | clarify | 指出冲突（PACKING、已完成、重复），问是否仍要外发 |
| ambiguous_reference | clarify | 列出候选订单，问一个具体问题 |
| missing_fields | clarify | 指出缺什么，不猜 |
| ineligible_suggestion | refuse | 给出具体不合格原因，并给出合格替代的估算 |
| not_in_data | decline-to-answer | 说明数据里没有，不编 |

## 打分规则

| 维度 | 判为正确的条件 |
|---|---|
| 行为 | 系统的内部子类映射到的官方类别与标准答案一致 |
| 分配 | 仅对 `allocate` 与 `ineligible_suggestion` 的替代：推荐车间与标准答案一致，或与标准答案同为按时且预计完成日相差不超过 0.5 天 |
| 解释 | 自动核查器找不到任何不在工具输出中的数字，且不合格原因、约束来源表述正确 |

一条请求可以行为对、分配错、解释对，三项分别计入。
