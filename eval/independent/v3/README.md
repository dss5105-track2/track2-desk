## 背景设定

和上次相同：

- 今天是 **2026-04-01** 早上。所有请求都是今天发出的外发请求。
- 请求按时间顺序到达。前面某条消息里说的"本周都别给某车间"这类话，对后面的请求也有效。
- 每家车间能不能接，看三件事：能做这个品类吗（`makes`），允许接吗（`status`），批量是否超过上限（`max_batch_pieces`）。

- v3 数据字典说明：群聊里的请求针对的都是 4 月 1 日仍在 `IN_PROGRESS` 的订单，"还在厂内生产"本身不算状态矛盾。

**这次新增：前面派出的单子会占用产能（全组已定按顺序处理）。**

- 只有判为 `extract / allocate`（有按时方案、直接派单）的请求才算派出去。追问、拒绝、无法回答、没有按时方案的请求都不占用产能。
- 粗算方法：从 `workshops.csv` 的 `current_queue_days` 出发。每遇到一条你判为直接派单的请求（包括上次已经分过类的 21 条里的，比如 R09、R12），按你会选的车间，把 `件数 ÷ 日产能` 加到那家车间的队列上；后面的请求用加过之后的队列。
- 选哪家车间：请求没有特别要求时，选最早能交回的那家；请求里有要求（最快、能按时里最便宜、缺陷率最低等），就按要求选。
- 只需粗算，拿不准就在"把握"里填 `低`。

## 四个官方类别

和上次完全相同，方便与 21 条的旧分类合并统计。

| 类别 | 意思 | 内部子类 |
|---|---|---|
| **extract** | 信息完整、要求合法，系统应该提取信息并给出派单方案 | `allocate`：有按时方案，直接推荐<br>`no_on_time`：信息完整，但任何车间都来不及，要说明晚几天并给选项 |
| **clarify** | 系统不能直接派单，应该先问人 | `ambiguous`：指代不清，数据里对应多张订单<br>`missing`：缺派单必需的信息<br>`state_conflict`：订单状态有矛盾，例如已经快做完了 |
| **refuse** | 请求指定了一家不能接这单的车间，系统应拒绝并说明原因、给替代 | `ineligible` |
| **decline** | 数据里根本没有答案，系统应说"无法回答"，不能编 | `not_in_data` |

注意区分：请求里说"别给某车间"是**用户约束**，系统照做即可，不算 refuse。只有"指定要给某车间、而那家不能接"才是 refuse。

## 判定顺序

每条请求按顺序问下去，第一个"是"就是答案：

1. 问的是数据里根本没有的东西吗？比如历史记录、价格、不存在的订单 → `decline`
2. 能唯一确定是哪张订单吗？不能 → `clarify / ambiguous`
3. 这张订单的状态和"要外发"有矛盾吗？ → `clarify / state_conflict`
4. 派单需要的信息缺吗，且订单表里也补不上？ → `clarify / missing`
5. 指定了一家不能接的车间吗？ → `refuse`
6. 以上都不是：粗算一下有没有车间来得及？有 → `extract / allocate`；没有 → `extract / no_on_time`

第 6 步只需要粗算：`队列天数 + 件数 ÷ 日产能 + 取送天数`，队列用按上面方法加过之后的，看能不能在交期前完成。
