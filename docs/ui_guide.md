# 调度员界面说明与演示脚本（第二轮）

```bash
streamlit run app/streamlit_app.py
```

界面只负责展示和把点击转成 `desk/pipeline.py` 里的调用。所有交期、成本、排序都来自 `kernel/`，界面自己不算任何数字。

设计目标：调度员一早上有 30 条消息、一个小时。界面要让他先处理最紧的，稳妥的一键过，每条卡片前三行就能做决定。

## 页面结构

| 位置 | 内容 | 对应的评分点 |
|---|---|---|
| 原左侧信息栏 | 保留标题、日期、目标、解析器、载入/重置、常驻约束和车间队列，直接显示 | 目标即配置；约束记录下达人 |
| 信息栏旁的窄导航 | 五个功能图标，悬停显示名称，点击切换，默认 Dispatch | 功能导航与原侧栏分开 |
| Dispatch · 固定底部 | **New chat message 输入框**：发送后自动显示这条消息的答案卡片 | 输入区始终可达 |
| Dispatch · 停工 | 群里报告某车间停工 → 卡片提示 → 确认后停派、重排，并列出已派批次，可一键改派；也可在 Workshops 页手动标记，侧边栏 Reopen 撤销 | 老师要求的停工场景 |
| Dispatch · 右上 | 五个分组、批量确认及订单列表，默认占主区约 38%；**新输入的消息排最前，其余最紧的在前**；可拖宽，超长时区域内滚动 | 找单、筛选和批处理 |
| Dispatch · 中左 | 当前请求、回答、候选车间和人工操作，独立滚动；变化提示在此区域顶部出现 | 解释可追溯 |
| Workshops | 车间登记册、当前队列图、“谁能接这批”查询 | 可查询的车间登记册 |
| Audit log | 账本记录（含返工时的最晚日期）、所有人工操作记录、下载 audit.json | 可审计的结构化记录 |
| Simulator | 官方模拟器实时运行：三个 baseline、简单规则分配器、全部目标设置；可切换 seed、是否取 10 个 seed 平均、是否 shock | 与 baseline 对比 |
| Evaluation | 四项评估是什么、怎么跑；当前目标下无人值守重放的结果 | 评估可复现 |

## 新消息输入区

原左侧信息栏完整保留：标题、日期、Objective、Message parser、载入/重置、Standing constraints、Workshop queues 均直接展示，未收进弹出框或折叠项。侧栏保留原有的拖宽和收起能力。五个功能图标另放在信息栏旁的窄导航，位置随侧栏宽度调整，不覆盖原侧栏；首次默认 Dispatch，悬停看名称、点击切页。Message parser 标签和选项均为 14px。

原侧栏中的 **Load morning inbox** 与 **Reset** 使用等宽列和固定 40px 高度，载入后禁用时尺寸不变，按钮功能保持不变。

侧栏标题与日期从一开始就固定在同一位置，下方设置、限制和队列在独立区域滚动，标题不会先移动一段才固定；主区空白状态不再重复显示品牌标题。

Dispatch 的 **New chat message** 固定悬浮在主区底部，左边缘与回答区对齐，采用浅灰蓝底色、浅边框和轻阴影。保留标题、From、Message、Send，通过缩小标题和留白降低初始高度（1440px 桌面约 142px）。控件并排且底部对齐；手机上保持紧凑同一行并隐藏长说明。切换到其他功能页时隐藏输入区。

- Message 是多行输入框。Enter 换行，点击 **Send**（或 Ctrl+Enter / macOS 上 Cmd+Enter）提交整个表单。
- 使用 `st.text_area(height="content")`，并在支持 CSS `field-sizing: content` 的浏览器中将输入区缩到一行：空白和短消息时，三个控件均约 40px 高（消息框内容区为 38px）。换行或折行时 Message 自动增高，From 和 Send 保持原高、底部对齐；消息框内容区达到 240px 后内部滚动，删短后缩回。不需要 Python 回调或额外 JavaScript。
- `field-sizing` 是渐进增强：现代浏览器使用紧凑单行起始样式；不支持该属性的旧浏览器回退为 Streamlit 原生多行自动增高，初始消息框可能高于 From 和 Send。Streamlit 1.50 已支持原生 `height="content"`，无需更改项目最低依赖。框内的原生快捷键浮层被隐藏，也不再展示输入区底部的快捷键说明，快捷键仍然有效。
- 保留原有 sender 选项、发送时去除首尾空白、空白消息不处理、提交后清空表单及跳转到请求卡片的行为。Send 只生成建议，人工确认后才写入派单账本。
- 输入区样式限定在 `dispatch_composer`。`app/desk_layout.css` 和 `app/desk_layout.js` 负责区域位置、实际输入高度测量、独立滚动及分隔线，不读取调度数据或修改账本。升级 Streamlit 后需复查这些局部 DOM 定位与布局。

## 收件箱与结果布局

桌面（至少 1000px）回答区在左，订单区在右，顶部对齐；订单区默认约占主区 38%。拖动中间分隔线向左可拉宽订单区，向右可缩窄，双击恢复默认。分隔线支持键盘左右箭头及 Home。宽度在同一浏览器标签会话内记忆，切分组、发送、确认及切页不会复位；为回答区和订单区保留最低可用宽度。

订单区压缩标题、控件间距和说明区留白，表格工具栏为 24px 高，小图标及展开按钮同步缩小。分类保持一行，窄窗口可横向滑动查看全部分类。

回答区独立滚动；订单区的标题、分类、批量确认与说明固定不动，只有下面的表格在限定高度内上下及左右滚动，横向滚动条留在可见区域底部。表格工具栏固定在表格上方，可直接搜索和下载。用 **Expand table** / **Close expanded table** 展开与收起订单表格；这两个操作不会派单，也不改变当前请求。展开使用独立的应用容器，避免强改原生全屏尺寸引起反复渲染。展开层只覆盖图标导航右侧、输入框上方的主区，不占据侧栏或输入区；关闭后回到原订单区。两区下边界随输入框实际高度调整。新请求或新的变化报告出现时回答区回到顶部，勾选候选车间不强制跳回。

窄于 1000px 时改为回答在上、订单在下；顶部导航显示图标和短文字，手机不依赖鼠标悬停。订单表格限制高度并可内部滚动，整页可继续上下滚动至所有操作；页面底部预留输入框空间。

新消息点击 Send（或 Ctrl/Cmd+Enter）后，会自动解析、切换到对应分组并显示回答/建议，无需再次点击订单；输入过程中不自动提交。真正派单仍需要人工确认。

未派单的候选表中，**★ 仅表示系统首选**，每行另有一个勾选框，最多选一家。下方保留 **Confirm 首选车间** 和 **Send to 勾选车间** 两个派单按钮；未选替代车间或选中首选时，右按钮禁用。原来的替代车间下拉框已移除。正常交期不满足的方案明确写 **Accept delay · send to …**；勾选本身不会写账本。

群聊回复草稿跟随选择变化，使用该候选真实回货日、返工日期、成本与交期；草稿明确等待人工确认。估算、候选顺序或推荐变动后，旧勾选失效，避免旧行号指向新车间。协商交期/上报保留在 **Other actions** 中；工具调用收为一行浅色 **View evidence**，点击展开查看。已派单仍通过 Done 中原有 Reassign 操作处理。

列表增加 **Customer（客户）**、**Product（产品）** 两列，直接读取订单簿；没有可识别订单的请求留空。保留原有单行选中、排序和卡片联动。列较多时可以在表格内横向滚动，页面本身继续响应式排列。

仅在 Needs a decision 分组下方显示 **Refused requests → Needs a decision**，被拒的请求仍在原分组。卡线推荐在列表中显示深橙色加粗的 **⚠ tight**，卡片增加橙色 **⚠ Late if reworked** 标记，含义是正常回货能按时、返工则会迟交；原有人工确认规则不变。

## 限制、停工和重新开放后的变化提示（真人测试任务 7）

解除限制（**Lift**）、消息带来新的禁令、确认车间停工（**Mark as stopped**）、重新开放（**Reopen**）后，当前页面立即显示变化报告：Dispatch 放在回答区顶部，其他页面放在该页标题下，自动将报告带入视野。已在当前页展示后，切回 Dispatch 不再重复，黄色更新行继续保留到下一次业务操作。

- 简短说明发生了什么、多少条未派推荐更新；统一用一个 **View changes** 折叠项核对请求、订单、前后车间/决定及已派批次。
- 有已派单时明确写出 **Already-dispatched batches are not changed automatically（已派出的单不会自动改动）**。有风险才逐条列出；没有已派单或风险时不展示对应的空区块。
- 有风险时提示进入 **Done → 选择请求 → Reassign**。返工迟交直接展示后端给出的回货日和交期；提示本身不会修改派单账本。原来重复的“重排成功”绿色提示合并到报告中。
- 有风险使用黄色警示，无风险使用蓝色信息框，延续现有产品配色。

报告先复制到 `session_state`，然后清空 `desk.last_change`；提示只渲染一次，刷新、切分组或选单不会重新弹出。折叠明细可以在当前页面直接展开。受影响的列表行显示黄色背景及 **↻ Updated**，查看卡片、切分组和普通刷新时保留，到下一次发送、确认、改派、约束操作、目标切换或重置时清除；新的变化报告会替换标记。

消息禁令的报告由后端预估生成。界面保持原有的下一次 `refresh_all()` 流程更新实际卡片，使用同一份报告展示提示和行标记，不在界面重新计算调度结果。报告中的数量取真实返回值，不写死示例中的 8 条。

复测：Reset → Load morning inbox → 按按钮上的实际数量一键确认 → 确认 R12 → Lift QuickStitch。当前 main 数据按这一流程返回 **5 条未派变化、10 条已派保持不变、1 条风险（R12）**。R12 仍派在 GiantWeave，返工回货 4 月 11 日、交期 4 月 10 日；打开 Done 才能主动 Reassign。再切到 Needs a decision 查看黄色更新行，提示不重放；发送下一条普通消息后旧标记清除。

## 请求卡片：前三行

1. **问了什么**：订单、件数、品类、交期（还有几天）、请求人的要求（最快、避开某家、点名某家）。
2. **系统的决定**：推荐车间、回货日、离交期还剩几天、**如果这批返工最晚哪天**、成本。返工也来得及是绿色；来得及但返工就晚是黄色。
3. **为什么**：一句话。例如“返工也能按时；它只做配件，所以两类都能做的车间留给更紧的单”。

下面依次是：数字核查标记、候选车间表（回货日、剩余天数、返工日期、排队、加工、运输、成本、缺陷率）、不合格车间及原因（直接列出，不用点开）、操作按钮、可复制的群聊回复、工具调用明细。

| 情况 | 颜色 | 按钮 |
|---|---|---|
| 有按时方案，返工也来得及 | 绿 | 确认推荐车间；或勾选别家，再点击 Send to |
| 有按时方案，但返工就会晚（“tight”） | 黄 | 同上；不会被批量确认 |
| 没有按时方案 | 橙 | 接受延误并派出；或选别家；重谈交期；上报 Boss |
| 点名了不能接的车间 | 红 | 用替代车间派出；或选别家 |
| 需要追问 | 蓝 | 复制追问话术；指代不清时直接选订单；输入请求人的回答让系统重新处理 |
| 数据里没有答案 | 灰 | 复制回复话术；标记已回复 |
| 已派出 | 紫 | 改派；查看审计记录 |

## 一键确认

“待确认”分组上方有一个按钮：**Confirm N safe recommendations in one click**。

- 只确认“返工也来得及”的推荐。
- 交期紧的（黄色）不会被批量确认，排在列表最前，留给人逐条决定。
- 如果某条稳妥的推荐要用的车间，正好是某条紧单也要用的，它也会被留下，提示先决定那条紧单。
- 按到达顺序逐条确认，每确认一条就按最新账本重算下一条；途中不再稳妥的会跳过。
- 这仍然是一次人工确认：按钮上的数字就是会派出的条数，结果会列出每条去了哪家。

官方 30 条载入后有 13 条待确认；一键确认数量及留下的原因以按钮和说明的实时结果为准，队列或约束变化后会重新核查。

## 约束是什么时候下的

“本周别给 QuickStitch”是 R12 在 08:48 说的。界面一次载入全部消息，所以 08:08 的 R04 打开时这条约束已经存在。界面的处理：

- 仍然对所有**未处理**的请求生效（现在派单就该遵守）。
- 但卡片上会写明：这条约束是之后才下的，因为请求还开着所以适用；并显示这条请求刚到达时的答案是什么。
- 评估用的无人值守重放按时间顺序逐条处理，不会把约束用到更早的请求上。

## 5 分钟演示脚本（Sprint 2 视频可直接用）

1. **载入收件箱。** 30 条进来，没有派出任何一单。指五个分组的条数：13 条待确认、7 条待决定、7 条待追问、3 条无法回答。
2. **一键确认。** 按按钮显示的实时数量派出稳妥推荐，顶部列出每条去了哪家。讲：留下的是系统认为需要人看的。
3. **R12，紧单。** 黄色：GiantWeave 周五回货，正好卡在交期当天，返工就晚一天。指左侧栏的约束：QuickStitch 本周不接新单，Boss 在 R12 下达。点确认。
4. **“已完成”里的 R04，为什么不选最快的。** 它去了 Little Loom 而不是最快的 Nimble Needle：Little Loom 只做配件，返工也来得及，把两类都能做的车间留给紧单。审计记录里写着当时最快的是哪家。
5. **R21，没有好选择。** R12 占用 GiantWeave 之后，R21 从黄色变成橙色，移到“待决定”：最早也晚 1 天。解释里写着“如果解除对 QuickStitch 的禁令，可以按时”。点左侧 Lift，先读顶部变化报告和 R12 的风险，再看 R21 回到可按时及列表更新标记。强调：已派单不会自动改变，要改派必须去 Done → Reassign。
6. **R08，拒绝。** FreshStart 单批上限 300，请求是 400 件。给出替代并可一键派出。
7. **R03，追问。** TrendCart 有 6 单在产，系统列出候选而不是猜。直接选订单，新请求自动生成。
8. **R18，无法回答。** ORD-999 不存在，系统说查不到，不编。
9. **Audit log。** 每一次确认、批量确认、改派、解除约束都有记录，可下载。
10. **Simulator。** 打开 10 个 seed 平均。讲：官方数据上我们和简单规则迟交率相同、迟交天数减半；数据一变我们更好，证据在评估报告里。

## 部署成公开 demo 链接

Sprint 2 首页需要可打开的 demo 链接。Streamlit Community Cloud 免费：

1. 用仓库所有者账号登录 https://share.streamlit.io ，授权读取 GitHub。
2. New app，仓库选 `dss5105-track2/track2-desk`，分支选合并了本轮改动的分支，入口文件 `app/streamlit_app.py`。
3. 部署。默认使用规则解析器，不需要任何密钥。
4. 部署后用另一台电脑、不登录的浏览器打开链接，确认能载入收件箱并确认一条。

**公开 demo 里不建议放 API key。** 链接是公开的，任何人都能触发调用、花掉额度。如果一定要在线演示 GPT-5：在应用的 Settings → Secrets 里填 `OPENAI_API_KEY`，先在 OpenAI 后台给这个 key 设很低的月度上限，演示完就删掉。不要把 key 写进仓库。

公开链接意味着任何人都能点确认。会话之间互不影响，刷新页面或点 Reset 就回到初始状态。
