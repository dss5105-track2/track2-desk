# SweaterCo 外协调度台 · 项目介绍

NUS DSS5105 Capstone · Track 2 · 屈妍玥、张锦若、吴杰、李岩、吴若晗、许佩瑶 · 2026-10-09

一句话：**让依赖群聊和经验的外发决策，变成经过验证、可以解释、能够追责的调度流程。** 英文贯穿语：From informal chat decisions to verified, accountable outsourcing dispatch.

## 1. 背景

**场景。** 针织厂 SweaterCo 自己做不过来时，把订单外发给 8 家合作车间。车间各不相同：QuickStitch 最快但质量不稳；SteadyHands 慢而稳；BudgetWorks 最便宜；Little Loom 只做配件，一天 70 件；GiantWeave 产能最大但取送慢；Nimble Needle 小单快；OldMill 因质量审计停业；FreshStart 试用期，每批最多 300 件。

**老师给的题。** 周一来了返单，十天后交，厂里已经满了，这批货今天就得发出去。“今天就发出去的厂，赢过周四才决定的厂。”现在怎么决定？有人在群里发一句：“@Chen，042 号单，1,500 件圆领衫，发给 QuickStitch，19 号要回来。”这句话就是决定，背后三件事没人系统地查：

1. **能做吗**：不是每家都做每种产品。
2. **现在排得开吗**：排了三天活的快车间今天不快。
3. **允许接吗**：一家停业整顿，一家试用期只接小单。

错任何一个，货隔天退回，在十天周期里这就是全部余量。

**老师给的材料。** 120 张订单、8 家车间的资料、一个所有组共用的模拟器（重放 120 张单子，报告迟交、周转、次品、成本、份额），以及 2026 年 4 月 1 日早上群里的 30 条外发消息。

**老师的要求。** 读群消息并做出四种正确反应（直接派单、先追问、拒绝并给替代、说“数据里没有”）；维护车间登记册；派前先估交期；派单附理由；处理没人能接的情况；留下审计记录。从四个目标里选一个主目标，再报一个其他目标和一个加权混合，和三个基线比，至少跑一次车间突然关门的 shock 场景。**AI 不做算术，回复里的每个数字都要能追溯到计算结果。**

## 2. 我们的故事线

汇报按六步讲：

1. **问题**：一句群消息就是决定，三个问题没人查，错一个货就退回。
2. **方案**：模型只负责读，算和定都在代码里，最后由人确认。
3. **为什么是迟交**：它相关、可测、可控。
4. **做出了什么**：流程跑通了，第一批结果在手，包括和简单规则打平这件事。
5. **风险**：还没有干净的语言测试；模拟器比现实宽松；策略不是全局最优。
6. **下一步**：留出集、停业检测、真人测试、公开 demo、评估报告。

贯穿的态度是**把弱点自己先说出来**：官方数据上和最快规则打平、语言模型的分数还不是干净的测试分数、事后最优能到 0 而我们没做到。老师原话：“说出哪里基线仍然赢，比赢本身更值钱。”

## 3. 为什么主目标选最少迟交

四个候选是：最少迟交、最少次品、分配公平、车间出事时扛得住。我们选迟交，三层理由：

1. **相关。** 交期是每张订单都明确写着的硬约束，群里几乎每条消息都带交期；快速响应这个岗位存在的意义就是保交期。次品、公平重要，但不是调度员每天最先问的问题。
2. **可测。** 模拟器记录每批货实际哪天回来，迟交率和迟交天数能直接算，没有歧义。公平没有业务定义，抗故障是一种测试条件而不是日常目标。
3. **可控。** 迟交由队列、产能、取送天数决定，正是换一家车间能改变的东西。次品率是车间的固定属性，调度只能决定“用不用高次品的车间”。

三个基线迟交 34% 到 92%，差距最大，这是补充证据，不是主要理由：基线差只说明基线差。

要老实说的一点：数据里没有客户报价、违约金、历史记录，我们**没法**严谨算出“迟交比次品损失大多少钱”。选迟交是数据能支持的、业务上最直接的那个。

**指标定义**：迟交率 = 晚于交期回货的批次 ÷ 全部批次；同时报平均迟交天数（按时为 0）。都是模拟器自带指标。

**宣布的护栏**：迟交相同时取周转短的。依据是老师题目把“周转天数和次品率”列为业务影响。

## 4. 混合目标怎么定的

混合目标是加权打分：每家车间得分 = 迟交 × 1.0 + 完工时间 × 0.3 + 次品率 × 0.25 + 负载 × 0.5，分低优先。

- **同一刻度**：每一项除以候选里的最大值，变成 0 到 1，权重没有量纲（老师要求天数、百分比、金额不能直接相加）。
- **怎么选**：迟交权重固定 1，扫描次品权重（0 到 0.6）和负载权重（0 到 1）共 20 组，50 个 seed。沿迟交–次品的权衡曲线走，**走到拐点就停**：次品权重到 0.25 为止，每多一个百分点迟交能换回几百件次品；再往上，每多一个百分点迟交只换回几十件（0.25 到 0.4 那一步，每点次品要付 17 点迟交）。
- **份额上限 30%**：最大车间 GiantWeave 的产能占比是 28.6%，取整；意思是没有一家车间拿到的活超过它的产能占比。
- **留出 seed 检验**（6000 到 6049）：hybrid 迟交 4.0%、次品件数占比 5.81%，比主目标少约 15% 的次品，多 2 个百分点迟交。
- **局限**：拐点是在官方 120 单上算的，换一批订单可能移动，Sprint 2 在新订单集上重扫。

## 5. 项目目标与成功标准

| 标准 | 现在 | 怎么测 |
|---|---|---|
| 官方 120 单迟交 ≤ 2%，正常和 shock | 1.7% / 2.0% | 共用模拟器，10 个 seed 平均 |
| 新订单上迟交少于最快规则 | 0.9% 对 1.7%（100 组扰动） | 规则定下来之后生成的订单集 |
| 留出集行为正确 ≥ 90%，答案先冻结 | 未测，10/15 第一次运行 | 四位同学手写 44 条 |
| 数字 100% 可追溯；“返工后”日期全守住 | 100%；shock 下 99% | 每条回复核查；1,200 批模拟 |

另外老师要求的：报一个其他目标（次品、公平、成本都有）、一个混合（上面那个）、至少一次 shock（已跑）、30 条消息按四类行为报（已做）、和简单规则对比（已做）。

## 6. 技术线

```
群消息 → 语言层（LLM 提取 + 代码核对）→ 内核（纯代码）→ 解释与核查 → 调度员确认 → 账本与审计
```

**语言层。** GPT-5 mini 从一句话里取出订单号、件数、交期、要求。然后代码逐项对照原文：订单号、客户、产品、车间名这些有固定词表的，原文里有就填上；原文里没有的值一律丢掉；件数必须是原文里出现过的数字，日期要对得上原文的日和月。原则：**模型提出，原文决定。** 没有 API 时自动退到规则解析器，所有测试和模拟实验都不需要 key。

**内核。** 三个资格检查（品类、状态、批量上限）在前。每家合格车间估两个日期：预计日期（队列 + 加工 + 返工期望 + 取送）和“如果返工最晚哪天”（加工时间多一半，和模拟器的返工规则一致）。排序按选定目标：

- **主目标（迟交）** 是一条三步规则：先留下返工后仍按时的车间（没有就留按时的，再没有就全留）；其中优先用途最窄的（只做一类、或有批量上限）；再相同选最早完成。道理：最早完成是贪心的，会把又快又灵活的车间花在交期宽裕的单子上，下一张紧单就没地方去了。
- **其他目标**是加权打分的不同权重；**use_slack** 是同一条规则、第三步改取最晚的稳妥完成（省成本，慢 5 天）。

**解释与核查。** 解释由计算结果生成，每个数字都要能在某次工具调用的输出里找到，找不到就标红。

**确认。** 人点确认才写账本和审计记录，确认后的单子占用后面请求的产能。老板说“这周别给 QuickStitch”，记下谁、哪条消息、几点，对后面的请求都有效。

**界面。** Streamlit。收件箱按下一步分五组（待确认、待决定、待追问、无法回答、已完成），最紧的排最前，每行直接写推荐哪家、哪天回、还剩几天。稳妥的推荐（返工也来得及、且不占紧单的车间）可以一键确认：早上 13 条里 7 条一键过，人看 6 条。

## 7. 评估怎么设计的

语言层分四项打分，老师要求决策和解释分开判：

| 项 | 判什么 |
|---|---|
| 字段提取 | 12 个解析字段对手工解析 |
| 行为 | 派单 / 追问 / 拒绝 / 无法回答对不对 |
| 决策 | 车间合格、约束遵守、有按时方案时按时、说“没有”时确实没有、偏好被遵守。由一份不调用系统代码的独立实现检查 |
| 解释 | 每个数字能追溯；回复里有这类回复必须有的内容 |

三套消息，干净程度不同，报告里要分开说：

| 消息集 | 来源 | 干净程度 |
|---|---|---|
| 官方 30 条 | 老师给的 | 开发集：系统是照着它改的 |
| 挑战集 38 条 | Claude 写的，换说法 | 半干净：AI 写的，两处修正参考过它 |
| 留出集 44 条 | 四位同学手写，答案先冻结 | 干净：10/15 第一次运行 |

标签：六人独立分类，kappa 0.70，25 条用多数票，5 条低于 5/6 一致的由全组按一条规则表决，10 月 7 日定稿，七类条数和老师公布的一致。

## 8. 目前的结果

**派单（官方 120 单，10 个 seed）**

| 策略 | 迟交率 | 平均迟交天数 | 平均周转 |
|---|---|---|---|
| 随机 | 34.2% | 6.13 | 21.9 天 |
| 挑最便宜的 | 91.8% | 81.9 | 106 天 |
| 最快规则（无 LLM） | 1.7% | 0.18 | 8.3 天 |
| **我们（迟交设置）** | **1.7%** | **0.09** | 9.3 天 |
| 混合 | 4.3% | 0.29 | 10.1 天 |

官方数据上和最快规则**打平**，迟交天数减半。换成规则没见过的数据，我们领先：100 组扰动 0.9% 对 1.7%（72 组更好、3 组更差）；收紧交期 4.5% 对 6.2%；加配件单 2.8% 对 4.0%；周日休息 2.1% 对 3.7%。简单规则仍然赢的地方：周转快 1 天，shock 下 1.9% 对 2.0%。

**交期承诺**：只报预计日期 94% 守约；报“返工后”日期 100%（shock 下 99%）。

**语言层**（行为正确率）

| | 官方 30 条 | 挑战集 38 条 |
|---|---|---|
| GPT-5 nano，改进前 | 86% | 84% |
| GPT-5 nano，改进后 | 100% | 97% |
| **GPT-5 mini，改进后** | **100%** | **100%** |

所有配置下回复里的数字 100% 可追溯。API 共花 1.31 美元。

**工程**：56 个自动测试；代码在 GitHub `main`；22 条失败案例已整理。

## 9. 已知局限

1. 官方数据上没有赢过最快规则，只是打平；事后知道全部订单的搜索能做到 0 迟交，我们还没做到。
2. 新规则的货平均比最快方案晚 1 天回来。
3. 语言层还没有干净的测试分数（留出集 10/15 出）。
4. 估算器不知道车间会突然关门，也不知道周日休息。
5. 界面没给真人用过，还没有公开链接。
6. 混合目标的权重在官方订单上选的，换一批订单可能变。
